# Registry-backed reference API

**Reference implementation, unaudited, for evaluation, not for production.** The service uses Node 22 built-ins only. `npm ci` is still supported through the committed lockfile; `npm audit` checks this package.

The API reads the registry with JSON-RPC `eth_call`. Every decision uses a block number fetched at the start of the request; the pause flag, asset check, version and hash are read at that same block. The existing `verifyAssetCompliance` call reverts while paused, so the service reads `paused()` at the pinned block and returns `DENY / REGISTRY_PAUSED` without attempting that reverting call. An unapproved asset returns `DENY / ASSET_NOT_APPROVED`. A live approved-asset read returns `ALLOW / ASSET_APPROVED`.

The current registry does not evaluate investor identity, amount, parties, or instrument terms. `amount`, `channel`, and `requestId` are validated and logged; only the live asset flag and pause state determine the decision. Request identifiers are caller-supplied correlation strings, not authentication, uniqueness, or idempotency controls.

The default listener is `127.0.0.1:8787`. Required environment: `RPC_URL`, `REGISTRY_ADDRESS`, `MB_API_KEY`. Optional: `API_HOST`, `API_PORT`, and `AUDIT_LOG_PATH`. All routes require `X-API-Key`, including `/health`. The JSON body limit is 8192 bytes. Unknown paths return 404. RPC calls have a two-second timeout and one retry. After both attempts fail, `/v1/verify` returns HTTP 503 with `decision: DENY` and `reasonCode: REGISTRY_UNAVAILABLE`; `/v1/policy` returns 503. The service never caches ALLOW. JSON-line records include request correlation, decision, policy version/hash and block number; unavailable reads use null for values that could not be read. HTTP `/health` reports process liveness only; it does not establish RPC health.

## Consumer client boundary

`compliance-client.mjs` is a small, dependency-free example for an application integrating this API. `verifyForTransfer` sends a fresh request with `cache: no-store`, pins the expected chain ID and registry address, validates the response decision, reason code, policy version/hash, block number, timestamp and matching request ID, and never stores a prior ALLOW. Defaults are one transport/timeout retry, a two-second per-attempt timeout and a five-second total deadline. Only transport/timeouts are retried; HTTP errors and malformed responses fail closed. The retry count is capped at two. An API process that is unreachable returns `UNAVAILABLE`; a live API reporting registry outage returns `DENY / REGISTRY_UNAVAILABLE`.

`executeTransferAfterAllow` invokes the supplied callback only after a complete valid ALLOW. Its tests use a callback spy and do not submit transactions. This is not a signer, wallet, transaction builder, production integration or atomic precondition: policy can change between the API read and a later transaction. The on-chain manager and its bound token independently check executor, asset and pause state during the transfer transaction. The API has no investor identity or eligibility inputs; request IDs are caller-provided correlation values, not idempotency controls.

Run tests with `npm ci && npm test`; inspect dependency advisories with `npm audit`. The client suite covers API outage, RPC-outage 503, timeout/retry limits, malformed and mismatched ALLOW responses, no transfer callback on non-ALLOW, and recovery via a fresh validated response. The reference API OpenAPI contract is `openapi.yaml`. The earlier file-driven mock is a separate fixture service, documented by `../api-spec/openapi.yaml`; it does not read this registry or enforce a transfer.
